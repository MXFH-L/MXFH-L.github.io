引言：当一个 30 步的任务在第 15 步崩掉

设想这样的场景：你让一个 AI Agent 帮你完成一个跨越 30 个步骤的复杂任务——读文档、调 API、写代码、跑测试、改 Bug、再跑测试……前 14 步它都干得不错。到第 15 步，它突然把第 3 步收集到的关键参数”忘了”，调用了一个根本不存在的工具，返回失败之后它选择了”任务已完成”，潇洒收工。

你换了一个更强的模型，又跑了一遍。这次它撑到了第 22 步。

问题真的出在模型本身吗？

过去两年，AI 圈在不断追逐”更好的提示词”和”更聪明的上下文”。但当任务从”写一段文案”升级到”完成一项工程”，我们终于意识到：模型不是马力不够，是没装上缰绳。这就是 Harness Engineering 想解决的事。

一、从 PE 到 CE 再到 HE：三种范式的演进

围绕 LLM 的工程实践，大致经历了三个层次：

范式 关注点 一句话定位
PE（Prompt Engineering） 精心构造单次指令 让模型这一次回答得更好
CE（Context Engineering） 为每个决策点动态构建上下文 让模型每一步都有合适的信息
HE（Harness Engineering） 设计完整的控制系统 让模型能稳定可靠地完成长任务

PE 和 CE 都是在”优化模型输出”，关注点仍然落在那次推理本身。HE 则把视野拉远了一层：它不再把模型当成主角，而是把模型当作整个系统中的一个组件——一个聪明但不靠谱的组件——并围绕它建造起一整套基础设施。

LangChain 团队把这件事浓缩成一个公式：

Agent = Model + Harness

Harness 字面意思是”马具、缰绳”。模型是那匹马，提供”思考”的力量；Harness 则是马鞍、缰绳、马蹄铁，负责让它真的能拉动车，而且不会撂蹶子把人摔下去。

二、模型的”先天缺陷”：为什么必须有 Harness

要理解 Harness 的价值，得先承认一个事实：LLM 本质上是 stateless（无状态）的。它每一次推理都是一次孤立的函数调用，所谓”记忆”只不过是把历史塞回上下文窗口里再让它看一眼。这种结构带来四个挥之不去的工程难题：

1. Context Rot（上下文腐烂）

随着对话或任务推进，上下文窗口越塞越满。即使没爆，模型的注意力也会逐渐发散——早期的关键信息被淹没在中段的工具输出和冗长的中间结果里。表面上”记得”，实际上”看不见”。

2. Hallucinated Tool Calls（工具调用幻觉）

模型可能调用根本不存在的工具，或者伪造工具的返回结果。这在长链路任务里尤其致命：一个虚构的 API 响应会顺着调用链一路污染下游决策。

3. Lost State on Failure（失败时状态丢失）

任务跑到一半崩了，怎么续？模型自己不知道刚才到第几步、改过哪些文件、留下哪些副作用。没有外部状态机，重启等于从零开始。

4. Early Stopping（过早停止）

任务还没真正完成，模型就笃定地说”已经完成了”。它对”完成”的判断完全依赖语言层面的合理性，而非真实世界的验证。

这四个缺陷没有一个能仅靠”换个更大的模型”或”写个更好的 prompt”彻底解决。它们是架构层的问题，必须用架构层的手段去对抗。

三、Agent Harness 是什么

Harness 指的是模型本身之外的所有东西。具体地说，一个完整的 Harness 至少包含：

  • System Prompts：系统级提示词，定义角色与边界
  • Tools / Skills / MCPs：工具与技能，包括其描述和调用协议
  • Bundled Infrastructure：捆绑的基础设施——文件系统、沙盒、浏览器等
  • Orchestration Logic：编排逻辑——子代理生成、任务交接、模型路由
    • 模型路由值得单独提一句：给一个 Agent 配置多个不同强度的模型，根据任务复杂度动态选择，在 Token 成本与推理性能之间动态取舍。MoE（混合专家）、Dense 模型、RPM（每分钟请求数）、TPM（每分钟 token 数）等概念在这里成为现实的工程参数。
  • Hooks / Middleware：用于确定性执行的钩子与中间件——上下文压缩、任务延续性、代码 lint 检查等

而 Harness 要承担的核心职责包括：

  • 工具执行
  • 内存管理
  • 状态持久化
  • 错误恢复
  • 上下文编排
  • 评估与度量：任务成功率、效率、成本、鲁棒性、安全性、一致性
  • 日志记录与可复现性

注意”评估与度量”被加粗了——这是把 Agent 从”能跑的 demo”变成”能上生产的系统”的分界线。没有可度量的指标，就不存在工程化。

不是模型的能力不够，而是你没有驾驭的能力。

四、判断一个系统是否采用了 Harness 架构：七大核心能力

架构是一种思想而不是某个具体框架。判断一个 Agent 系统是否真正采用了 Harness 架构，可以对照下面这七项能力：

1. 规划能力（Planning）

把大任务拆成可执行的小任务，并能根据进展动态调整计划。计划本身需要持久化、可观察、可被人类介入修改。

2. 虚拟文件系统

对抗 Context Rot 的核心手段。让 Agent 把中间产物（搜索结果、API 响应、草稿等）写入”文件”，需要时再按需读取。本质是把”工作记忆”从有限的上下文窗口外置到外部存储——和人类用纸笔做笔记是一回事。

3. 任务委托 / 子智能体（Sub-agents）

把子任务分派给独立的子智能体，实现上下文隔离和算力分配。父 Agent 只看到子 Agent 的最终摘要，不必把它整个工作流都塞回自己的上下文里。

4. 上下文管理

这是一组组合拳：

  • 输入上下文：系统提示词、待办列表、长期记忆、技能、文件系统工具说明等，在启动时注入
  • 运行时上下文压缩：卸载大型工具输入和结果到外部存储
  • 摘要化：用模型自己生成精炼摘要，替换冗长的历史
  • 长期记忆：跨会话保存关键信息

5. 代码执行与安全沙箱

遵循 “Trust the LLM + 隔离执行环境“ 的安全哲学：信任模型的判断力，但把它关在沙箱里。允许它写代码、跑代码，但不允许它伤到真实环境。

6. 人工介入（Human-in-the-loop）

关键决策点必须可以暂停、等待人类确认。一个不能被人类拦截的 Agent，是一颗按了启动按钮的炮弹。

7. 技能包加载与管理（Skills）

按需加载领域技能，而不是把所有工具一股脑塞给模型。技能是可组合、可分发、可升级的——这一点正在让 Agent 生态走向类似软件生态的形态。

五、总结：架构是一种思想

回到开头的那个崩在第 15 步的任务：真正的解法不是再换一个更聪明的模型，而是给它装上 Harness——加一个虚拟文件系统让它不会忘事，加一套子智能体让它能分工，加一层沙箱让它敢于出错，加一组 Hook 让它在压缩上下文时不丢关键信息，加一个人工介入入口让你能在它走偏时及时拉缰绳。

Harness Engineering 不是某一个 SDK，也不是某一个开源框架，它是一种架构哲学：承认模型的不完美，并用工程化的方式去补足那些不完美。

如果说 Prompt Engineering 教我们如何”提问”，Context Engineering 教我们如何”喂料”，那么 Harness Engineering 教我们的是——如何驾驭。

把模型当成一匹烈马，而不是一个许愿池。
然后，给它装上缰绳。
